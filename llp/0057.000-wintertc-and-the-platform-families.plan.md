## Summary

Charlie asked two things on 2026-09-03: *"In ibex2, it seems like we probably
want to implement WinterTC in Rust? And then also some other things like a way
to access the filesystem, securestore, a few other things. What does that list
look like?"* — and, after the list: *"it might be kind of nice if these things
were optional modules that you could add in? or should they all be part of
ibex2? maybe if they are small it's better to just include them."*

This document records the list as measured against the crate on 2026-09-03,
decides the packaging shape, and orders the work. Three findings shape it:

- **Both consumers ask for a strict subset of WinterTC.** Exact 2's LLP 1027
  D10, accepted today, wants "the WinterCG minimum minus time and streams" as
  Rust bindings; Snapback 2's effects (LLP 1003 §1) want `fetch`, `console`,
  timers, `URL`, the text codecs, and `randomUUID`. WinterTC is therefore the
  right *ceiling* for the JavaScript tier — it is what npm packages target,
  and LLP 0057 OQ2 says Exact 2 will run npm code — while LLP 0059 §7's rule
  still orders what gets built.
- **"In Rust" is true for about half of WinterTC.** Per LLP 0057 §3.1 Rust
  owns bytes, parsing, state the platform touches, and transport; object
  plumbing — `EventTarget`, `AbortController`, the stream controllers — is
  JavaScript over Rust. §2's table says which, item by item.
- **The Expo-shaped list is the grant-family pattern, not a new mechanism.**
  Five families exist and three are specified. Each platform capability below
  is one more: a parameterized question, a Rust trait, a platform backend, a
  JavaScript binding, a no-engine test. Two pieces of infrastructure come
  before most of them (§4), and the packaging answer (§5.1) is: *in the
  crate, feature-gated where a family pulls a dependency or a platform
  framework, never a plugin.*
- **One implementation, three doors (§5.0, added later the same day).**
  Every capability is a Rust function the library exposes; the bindings
  project it into a JSI runtime the caller owns and never touch a loop; the
  runtime is one caller of the bindings. Exact 2's `exact-js` needs door 2
  with nothing behind it, which is what showed the first cut of L1 was
  wrong and turned D4 into three crates.

Implementer and date are named per lane when a lane starts (§6). Only what
runs binds; this is a plan.

## 4. Three things that come first

Each is one design, and each blocks a column of the tables above.

**Events into JavaScript.** `task.rs` delivers two things: settlements and
timers. WebSocket messages, a location watch, a notification, a network
change, an incoming URL — every event-bearing family needs a *subscription*
whose deliveries enter the one sequence-numbered FIFO LLP 0058.000.000 §8
requires, so an application observes one order between a timer, a settlement,
and an event. For the Rust consumer this forces LLP 0068 OQ3: a synchronous
binding cannot deliver an event. Designed once, in lane L3; `WebSocket` is
its first user.

**The OS permission as a second gate.** The manifest grant is the runtime's
authorization. iOS and Android add a prompt and a usage string; macOS adds
TCC. A binding must report *granted by the manifest, refused by the OS* as its
own error, distinct from a denial, so a consumer can prompt rather than
conclude it was never allowed. LLP 0067 §3 gains that sentence with the first
OS-gated family (lane L5), not before.

**The cut LLP 1027 D9 asks for.** `exact-js` links the engine adapter, the
`fetch` binding and its pump, and the pure tier's bindings — never the loader,
ESM lowering, `require`, or timers. Today those are one crate with `hermes`
and `loader` features and one binding installer. That cut is owed to an
accepted RFC and is lane L1.

## 5. Packaging — the three doors, then: included, gated, or a crate

### 5.0 Three doors, one implementation

Charlie, later on 2026-09-03: *"we want to split things so that the
implementation of stuff in ibex2 can be called from rust directly (with no
JS/TS involved) or from TS, so we should structure our design
appropriately."* Measured against the crate and against what exact2 built
the same day, there are three ways in, and the design rule is that the
second never depends on the third.

**The library** — `ibex2::stdlib` and `ibex2::host`: Rust functions over
Rust types, authority carried by `Bindings` (LLP 0068). Door 1: Rust calls
it. Exact 2's hosts do, today, with no engine in the process.

**The bindings** — the projection of the library into a JSI runtime *the
caller owns*: the C ABI (`ibex2_host_call`, `ibex2_async_begin`, the
handle table), the value marshaling between `AbiValue` and `jsi::Value`
(`to_abi` and the zero-copy byte return in `hermes_shim.cc`), the JavaScript
shapes as bytecode (`url.js`, `headers.js`, `fetch.js`, …), and the
completion queue with its pump (`task.rs`, `pool.rs`). Door 2: TypeScript in
anyone's runtime. Installed by one function, `ibex2_install(runtime,
bindings, groups)`, which takes a `jsi::Runtime` it did not create and the
library's endowed `Bindings`, and returns.

**The runtime** — ibex2's own engine embedding: create and destroy, the
loop that waits on the queue's condvar with the next timer as its timeout,
the loader and ESM lowering and TypeScript stripping, the bytecode cache and
the receipt, the timers group, `harden`, the global-name assertion (LLP 0067
R5), and `ibex2 run`. Door 3: a JavaScript *program*. Snapback 2's effects
use exactly this (`Hermes::new`, the installers, `harden`, `pump`). **The
runtime is a caller of door 2** — it installs bindings through the same
function `exact-js` would, which is the proof that there is one door and
not two.

Why this is the split and not a preference: `exact-js` (LLP 1027 D3, stage
1 landed 2026-09-03) creates its own lean-VM runtime in ~170 lines of C++,
drives it from the runner's own loop (`__exact_call` / `__exact_settle` /
`__exact_fulfill`), and routes `fetch` through the runner's ticket path so
the agent sees every request (D1a). It wants none of ibex2's runtime — no
loop, no loader, no timers, no `fetch` binding — and it owes itself "the
pure tier as ibex2 bindings (`URL`, `TextEncoder`, base64, `Headers` from
Rust)" for one reason LLP 1027 D10 states: the grant checker in the library
and the module in the engine must parse a URL with *one* parser. That is
door 2 with nothing behind it. LLP 0057 §3.1's "one implementation serves
[the Rust consumer] directly and the JavaScript bindings thinly" said the
same thing before there was a second runtime to install into.

Six rules, each checkable:

- **R-a. The library never references the bindings or the runtime.** True
  today with one exception found by checking: `stdlib/headers_ops.rs`
  operates on `Headers` *handles* in the queue's table (`task::RuntimeState`)
  — it is the JavaScript mutation surface over handles, which is the
  bindings' business, in the library's directory by accident. It moved to
  `bindings/headers_ops.rs` in L1a on 2026-10-04;
  `stdlib::fetch::Headers` itself, which it wraps, stays.
- **R-b. The bindings never create, drive, or wait on a runtime.** They take
  a `jsi::Runtime&` and return; async work completes into the queue, and
  `pump` delivers *when called*, on the runtime's thread, followed by a
  microtask drain — the contract `task.rs` already states as
  `Pump::CONTRACT`. The queue *offers* a condvar wait; only the runtime
  uses it. No sleep and no blocking call anywhere in door 2.
- **R-c. Install takes the library's `Bindings`, not a grant set.** A
  JavaScript `fetch` is the projection of a Rust `Fetch` value — one object,
  one grant, one check. Implemented in L1a: `Context::from_bindings` retains
  the transport, stores, mounts, provider, and grants from exactly the value
  `Host::endow` returned; `Adapter::install` consumes that endowment rather
  than a raw grant pointer. A borrowed runtime uses the `Context`'s state by
  pointer identity. An owning Hermes runtime keeps its already-constructed
  state and adapter, then copies the endowed transport, stores, environment,
  optional provider, and directories into that state before installation; it
  neither reconstructs platform defaults nor shares a task namespace with
  another runtime. `Context::new` remains only the convenience spelling for
  `Host::new().endow(grants)`.
  This is LLP 0068 §1's "not a second implementation" made structural.
- **R-d. Groups are named and independent.** `pure` (`URL`,
  `URLSearchParams`, `Headers`, the text and base64 host calls), `console`,
  `fetch`, `fs`, `env`, `secrets`, `kv`, `timers`, and from L2 and L3
  `crypto` and `events`. A caller installs the ones it wants; the runtime
  derives `ALLOWED_GLOBALS` from what it installed. `exact-js` installs
  `pure` and *not* `fetch`, because its `fetch` is the ticket path — and
  that is the door working as intended, not a gap.
- **R-e. One engine build.** The bindings' bytecode and the caller's VM come
  from the same `hermes-lean-sys` (D4): the bindings compile their
  JavaScript with that crate's `hermesc` at build and link no VM; the
  caller links the VM; the receipt (`bytecode.rs`'s coupling) says they
  match. Today both repositories point at `ios/Frameworks-vanilla` by path,
  which is the same thing by convention and not by construction.
- **R-f. Threads.** The library is `Send + Sync`; a runtime handle is
  thread-affine; only the queue crosses. Already the shape (`task.rs`).

The web is the fourth caller, and it is why WinterTC is the contract rather
than a convenience: Exact 2 runs the same TypeScript module in the browser
(LLP 1027 D6), where the browser's own `URL` and `Headers` are the
bindings. A module written to WinterTC runs under door 2 on native and under
the browser on the web with no shim in between, and WPT is how the two are
held equal.

### 5.1 Included, gated, or a crate

Charlie's leaning — *if they are small, include them* — is the answer, with
the number that makes "small" checkable and the one thing that must never be
optional.

**D1 — The families are one closed enum in the core, never a plugin.** The
check is one chokepoint over one grammar (LLP 0067 §3). An open registry of
families is exactly the apparatus Ibex 1 grew around its registry, and a
separate crate cannot add an `Operation` variant without it. The grammar and
the admit for every family live in `grant.rs` and `boundary.rs` whether or not
the family's backend is compiled.

**D2 — What is optional is what a family pulls in.** A family whose Rust is a
few hundred lines and whose backend is a system call is simply in. A family
that pulls a third-party crate or links a platform framework is a cargo
feature on `ibex2`, **default on**, named for the family — `crypto`,
`websocket`, `location` — the shape `hermes` and `loader` already have.
Off, the binding is present and refuses with a named `Unavailable`, the same
way LLP 0068 §1 has a consumer granted nothing hold bindings that refuse
rather than absent ones: `Bindings` keeps its shape and a consumer's code
compiles either way. Exact 2's own rule — an optional capability is a
separate artifact, never a cargo feature on a core crate — is about Exact 2's
crates; `ibex2` is a dependency its hosts already link with
`default-features = false`, and a feature here only ever widens what is
*linked*, never what is *granted*. Feature unification across a workspace
therefore costs bytes, not authority.

**D3 — Backends are traits a consumer substitutes; a separate crate can be a
backend, never a family.** `Transport`, `SecretStore`, and `KvStore` are
already this, through `Host::with_transport` and its siblings. Every family
below gets the same: the trait and the default backend in the crate, and a
consumer with its own — a test, a platform ibex2 does not build for, an
enterprise store — hands one in.

**D4 — Three crates, one per door that links differently.** *(Revised
later on 2026-09-03 for §5.0; proposed, see §8 OQ5.)*

- **`ibex2`** — the library and the bindings. The library always; the
  bindings behind a `bindings` feature, off by default, which needs the JSI
  headers and `hermesc` from `hermes-lean-sys` at build and **links no
  VM** — the caller's binary provides the engine and `libjsi`. The
  per-family features of D2 sit here too. Consumers: Exact 2's hosts
  (library), `exact-js` (library plus `bindings`).
- **`ibex2-runtime`** — the runtime. Depends on `ibex2` with `bindings`
  and on `hermes-lean-sys` for the VM; carries `loader` (Oxc) as its
  feature, the timers group on, `harden`, the R5 assertion, the `ibex2`
  binary, `examples/speed`, and the engine tests. Consumers:
  `snapback2-effects` (today `ibex2` with `hermes`; a pin bump on their
  side, which LLP 0057 §5.2 says a pin is), and the CLI.
- **`hermes-lean-sys`** — the engine build, as LLP 1027 D9 item 2 and its
  §9 stage 6 propose and this repository owns: the vanilla lean VM and
  `hermesc` per platform, the receipt, the headers and link lines. A
  build-dependency of `ibex2[bindings]`, a dependency of `ibex2-runtime`
  and `exact-js`. It replaces the directory-and-path in two `build.rs`
  files, and it is where the Linux lean build and the iOS device
  measurement (LLP 1027 §10 Q7) get done once.

Why crates and not features for *this* cut, when D2 chose features for the
families: R-b is a rule about dependency direction, and a feature cannot
express "this module may not use that one" inside one crate — a crate
graph can, and the compiler enforces it. It also makes `exact-js`'s "no
ibex2 runtime symbol in the binary" a fact of the graph rather than a
review item, and it matches Exact 2's own rule (an optional capability is a
crate, never a feature on a core crate — LLP 1027 D3 made `exact-js` one
for the same reason). The families stay features because a family is not
a layer: it never changes who links what, only what a binding can reach.

**D5 — "Small" is a number, recorded not remembered.** Every default-on
family is a row in `metrics/ibex2-speed.jsonl`: its stripped size delta on the
run-only binary and its delta at the floor. Proposed, for Charlie to set:
default on at **≤ 150 KB and ≤ 50 µs**; above either, off by default and named
in the consumer's `Cargo.toml`. Diagnostic like the rest of `metrics.mjs`,
never a blocking check — `rules/RULES.md` §Agents forbids adding one without
the human saying so.

**D6 — A consumer chooses its modules twice, and never the grammar.**
*(Charlie, 2026-10-04: "is it possible for us to make ibex2 one of those
things where you can choose which modules to include?" and, to the shape
below, "your suggestion sounds right.")* There are two choices and one fixed
part:

- *What is linked* is chosen with cargo features (D2). Off means the
  family's Rust code and its dependencies are not in the binary.
- *What is in a runtime's global object* is chosen with install groups
  (R-d): `ibex2_install(runtime, &bindings, groups)`. A group not installed
  has no globals, costs nothing at startup, and adds nothing to freeze. The
  runtime derives its allowed-globals list from the groups it installed,
  replacing the fixed `ALLOWED_GLOBALS`.
- *Fixed:* every family's grant grammar and admit stay compiled in (D1), so
  a manifest line means the same thing in every build, and a family whose
  feature is off refuses with a named `Unavailable`.

Defaults: a family within D5's budget is default on, so a consumer opts out
of what it doesn't need. A family over the budget is default off, so a
consumer opts in by name. Whether the runtime picks its capability groups
from the manifest (no `net.fetch` grant means no `fetch` global, the
`process.env` model) is left to L1 to decide on measurement. Groups land
with L1; each family's feature lands with its own lane, together with its
D5 row.

**Streams stay out of this program** (Charlie, 2026-10-04, after weighing
them: "let's skip streams for now. seems like they are big and heavy").
No engine-agnostic Rust implementation exists to reuse: Deno and Node
implement them in JavaScript, and workerd and Servo bind them to their own
engines. If a call site arrives, the cheapest conformant path is the
vendored `web-streams-polyfill` behind a `streams` feature (default off
under D5), with `Response.body` wired to the existing Rust body stream.

## 6. The lanes, in order

Ordered by who is waiting. Each names its scope, its split, what it touches,
and what *done* means. Implementer and date are filled in when a lane starts;
a lane that starts links this document into `llp/current/` if it has been

### L1 — The bindings door

*(Rewritten later on 2026-09-03. The first version had a consumer link the
engine adapter, the `fetch` binding, and the pump without the loader or
timers. No consumer wants that: `exact-js` has its own adapter, loop, and
`fetch`, and needs bindings installed into a runtime it created.)*

*Scope.* §5.0 as code: door 2 exists, the runtime is its first caller, and
`exact-js` is its second. The engine build moves behind `hermes-lean-sys`
(D4) in the same lane, because R-e is what makes bytecode from one crate
safe to evaluate in a runtime from another.

*Touches, by where each file lands.* The library stays where it is
(`stdlib/`, `host.rs`, `grant.rs`, `boundary.rs`, `secrets/`, `kv.rs`,
`transport/`, and the two Objective-C++ backends, which move out of
`engine/` since they never were the engine's). The bindings stay in `ibex2`
behind `bindings`: `boundary_abi.rs` less its loader ops and drive
primitives; `task.rs` less `LoaderConfig`, `load_module`, and `grants_for`,
which are the loader's and were in the queue's state by accident; `pool.rs`;
`stdlib/headers_ops.rs`, renamed out of `stdlib/` (R-a); `bindings/*.js`
less `esm.js`, `harden.js`, and `testharness.js`; and the
install half of `hermes_shim.cc` as `bindings/install.cc` — `to_abi`, the
byte return, `set_binding`, `make_async_binding`, the group installers, and
the one entry point `ibex2_install(runtime, bindings, groups)`, compiled
against JSI headers only. The runtime moves to `ibex2-runtime`:

### L2 — `crypto`

**Randomness portion implemented 2026-09-06, Codex.** The two OS-random
functions, Rust/no-engine API, JS bindings and their WPT subset are in
0059.000 §3.9. They are always available: one small existing-workspace
`getrandom` dependency, no family feature or new engine requirement.
`DOMException` and `QuotaExceededError` are the error-shape prerequisites.
The algorithm/key portion below remains unimplemented; this lane is partial.

*Scope.* `crypto.getRandomValues` and `crypto.randomUUID` (0059.000 §3.9),
then `crypto.subtle` at exactly §3.14's algorithm set — digest SHA-256/384/512;
HMAC; ECDSA P-256; Ed25519; AES-GCM; HKDF and PBKDF2; `importKey`/`exportKey`
in `raw`, `pkcs8`, `spki`, `jwk`; `generateKey`. No RSA, no SHA-1, no MD5.
Ungated, as §3.9 argues: computing a digest conveys no authority.

*Split.* All Rust: `stdlib::crypto`, pure, no host needed — the Rust consumer
calls it directly. `CryptoKey` is an opaque handle in the boundary's table;
material crosses only on `exportKey` of an `extractable` key. JavaScript is a
thin `crypto.js`. The CSPRNG is the platform's through the `getrandom` crate.
The algorithm crates are the first D2 decision: RustCrypto's set
(`sha2` is already a dependency; `hmac`, `p256`, `ed25519-dalek`, `aes-gcm`,
`hkdf`, `pbkdf2`) against `ring`, which rustls already links off Apple —
chosen in the lane by the D5 size row, since the API is the same either way.
Feature `crypto`, default on.

*Done when.* The WPT WebCryptoAPI subset for the listed algorithms passes
under the testharness binding; a known-answer vector per algorithm in Rust; a
Snapback effect can call `randomUUID()`; `ALLOWED_GLOBALS` gains `crypto`;
the D5 row is recorded.

### L3 — Events, abort, and the second direction

*Progress, 2026-10-04.* The Rust direction is implemented: events are the
third `HostTask` kind in the existing FIFO, every admission receives a
monotonic sequence under the queue lock, and a `Subscription` cancels queued
but unreserved deliveries. The Rust consumer proof uses an
`std::sync::mpsc::Receiver` and links no engine. The door-2 projection is also
implemented: the adapter owns each callback root together with its Rust
`Subscription`, event payloads are delivered only from `pump`, and detach
unsubscribes before releasing every root. The `EVENTS` group now supplies the
JavaScript surface and rebases AbortSignal on EventTarget when both groups are
selected. The WebSocket source remains L4.

`EVENTS` requires `PURE` solely for `DOMException` (`dispatchEvent`'s
`InvalidStateError`) and has no timer dependency. `AbortSignal.timeout()` is
present whenever `ABORT` is installed and throws `NotSupportedError` when
`TIMERS` is absent; making all of `ABORT` depend on timers would violate the
independent-group rule. `AbortSignal.any()` flattens dependent sources, marks
all dependents before dispatch, and releases those source registrations after
abort.

The global object keeps its engine-owned prototype. Making that host object an
`EventTarget` by prototype mutation would make the engine's root shape a
binding implementation detail. Instead `events.js` gives `globalThis` an
internal listener record and installs the three forwarding methods as own
properties; `self` is exactly `globalThis`. `navigator.userAgent` is the stable,
truthful `Ibex/0.1.0`, matching this crate version.

Vanilla Hermes at pin `6badada762121682b5481b6124e6c3a991ae6046`
exposes `HermesInternal.enablePromiseRejectionTracker`, not the later Ibex
checkpoint hook. Its upstream JavaScript tracker needs `setTimeout`, calls
`onUnhandled(displayId, reason, promise)` after 100 ms for
`ReferenceError`/`TypeError`/`RangeError` and after two seconds otherwise, and
calls `onHandled` only for a rejection it already reported. The adapter enables
it when both `EVENTS` and `TIMERS` are installed. Without timers the handler
properties and manual events still exist, but automatic rejection tracking is
unavailable. Enabling the upstream tracker replaces Hermes's private
`Promise._B`/`Promise._C` callback slots; the adapter records those two exact
trusted replacements in the pre-hardening integrity baseline, after which the
normal harden walk freezes them. `reportError`, EventTarget listener failures, and exceptions
escaping pumped timer/subscription callbacks dispatch a cancelable `error`
event and use the existing console-error path only when default was not
prevented. A top-level `eval`/module-body exception remains the entrance's
checked error result; it is not also turned into a global event.

The pinned, unmodified DOM-tree-free WPT subset is 75/75: eight
`dom/events/*.any.js` files and four `dom/abort/*.any.js` entry files (with
the latter suite's one unmodified resource). The runtime and binding compiler
both explicitly enable Hermes's ES6 block-scoping option; without it, source
fixtures and binding bytecode disagree about per-iteration `let` capture.

The D5 release measurement compares this lane with its stack base
`4df8724d`, using identically `strip -x`-stripped run-only binaries: 4,424,464
bytes without the family and 4,458,448 bytes with it, a 33,984-byte delta.
The Rust-only paired floor probe (install + harden + first evaluation, runtime
construction excluded) observed +86.5 µs in its lowest-load run and
+86.5–167.2 µs across four runs. The size is below D5's proposed 150 KB line;
the startup result is above its proposed 50 µs line. OQ1 still reserves those
thresholds for Charlie, so L3 records the result and keeps `EVENTS` in
`DEFAULT` rather than converting a proposal into policy.

Three halves that ship together, because the first two are useless without
the third's cancel path and the third is untestable without the first two.

*JavaScript plumbing.* `Event`, `EventTarget`, `CustomEvent`, `ErrorEvent`,
`PromiseRejectionEvent`, `DOMException`, `AbortController`, `AbortSignal`
(with `timeout()` and `any()`), `reportError`, `self`, `navigator.userAgent`,
and `onerror`/`onunhandledrejection`/`onrejectionhandled` wired to Hermes's
promise-rejection tracker. One `events.js`, compiled to bytecode like the
rest. `ALLOWED_GLOBALS` grows by exactly those names.

*Cancellation in Rust.* `Request` gains a cancel token; each transport honours
it — `NSURLSessionTask.cancel` on Apple, a flag checked between reads in the
rustls and dev-TCP transports. An aborted `fetch` rejects with an `AbortError`
`DOMException`, worded once in Rust.

*The subscription.* `HostTask::Event { subscription, payload }` as a third
variant in the one FIFO of `task.rs`; a `Subscription` handle on the Rust
side with one other operation, unsubscribe; the pump delivers into the
callback the binding registered. For the Rust consumer, LLP 0068 OQ3 is
answered here as the smallest thing that works: a `watch` returns a
`std::sync::mpsc::Receiver`, the consumer's loop blocks or polls, and no async
runtime is chosen for anyone.

*Done when.* A test in `task.rs` admits a timer, a settlement, and an event
and observes them in admission order; an in-flight `fetch` aborts observably
on all three transports; the WPT subsets for `AbortSignal`, `EventTarget`,
and `DOMException` pass (the pinned event/abort subset is 75/75); a Rust consumer test receives events on a
`Receiver` with no engine linked.

### L5 — Platform families with a named consumer

The §3 table, in cost order, and **none before a consumer names it** —
LLP 0059 §7 and LLP 0067 §8 order this lane, they do not schedule it. What
each costs, so the first ask is cheap:

1. **`device.read <name>`** — model, OS and version, app version and build,
   bundle identifier, locale, time zone. The `process.env` shape: a snapshot
   of the granted names, absent rather than refused. Apple: `sysctl`,
   `NSBundle`, `NSLocale`. Linux: `/etc/os-release` and the environment. No
   OS gate. Gated by name (§8 OQ3).
2. **`net.state`** — online, interface type, and a change subscription.
   `NWPathMonitor` on Apple; on Linux, honest `unknown` until a call site
   pays for netlink.
3. **`link.open <origin>` and the incoming-URL subscription** — the
   AuthSession shape. ibex2 owns the grant and the subscription; the host
   owns scheme registration and hands the redirect in.
4. **`clipboard.read` / `clipboard.write`** — `NSPasteboard`/`UIPasteboard`;
   Wayland and X11 are a decision, not a default.
5. **`notify.*` and `location.*`** — the first OS-gated families; the
   LLP 0067 §3 sentence from §4 lands with whichever is first, and the
   binding's error taxonomy gains *refused by the OS*.

Every one ships the §3 checklist whole — the grammar line, the admit, the
trait with three backends, the `Bindings` field, the binding, the no-engine
test, the metrics row, the LLP 0067 row.
