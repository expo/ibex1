## Summary

This Spec defines the engine-independent contract that lets Ibex 2 use a
pinned, unmodified Hermes while Rust remains the runtime capability-security
kernel. Rust mints authenticated capability contexts, derives operation
bindings, authorizes effects, retains async authority, and owns resource
lifetime. The engine adapter creates JavaScript callables and host objects
that carry opaque native tokens, translates typed values, and schedules work;
it never discovers authority from JavaScript frames, Promise jobs, globals,
thread-local state, or a default principal.

The vanilla secure posture uses bearer/object-capability semantics. Invoking a
bound callable uses the authority captured by that binding. Deliberately
passing, exporting, re-exporting, or scheduling it delegates the same
authority. Shared-realm integrity prevents authority discovery through global
or intrinsic interposition, but this posture does not isolate mutually hostile
modules within one realm; LLP 0058.000 assigns that claim to a patched or
process-isolated tier.

Existing `CallContext`, `HostHandle`, timer, and adapter code is prototype
input only where it accepts engine-derived principals, JavaScript scalar
handles, construction globals, or the legacy composition root. LLP
0058.000.001 requires a separate greenfield implementation of this protocol.

## 1. Scope and normative language

The key words **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are normative.
This Spec covers:

- Rust context, binding, callback, completion, and resource records;
- the logical Rust/engine adapter interface;
- module binding, shared-global, bootstrap, and namespace-caching rules;
- inline and async invocation order;
- delegation, attenuation, revocation, and teardown;
- task/microtask handoff and timer behavior;
- refusal classes and safe error materialization; and
- conformance for the vanilla secure posture.

It does not specify an FFI byte layout, a JavaScript module syntax, transport
implementations, VFS/network stage algorithms, or a replacement Promise
implementation. Those may vary without changing this contract. No conforming
implementation may require a Hermes-private symbol.

## 2. Security invariants

The following invariants hold in every vanilla secure artifact:

1. **Rust provenance only.** Every capability-bearing invocation starts from a
   live Rust-minted binding. Missing provenance fails closed; it never means
   root, principal `0`, the current thread, or the current frame.
2. **No scalar authority entry point.** JavaScript cannot invoke a generic
   dispatcher by supplying a numeric, string, byte-array, or property-readable
   handle. Authority enters only through a native closure or a host object's
   private native slot.
3. **Exactly one authorization path.** Every reachable effect either refuses
   or joins exactly one typed Rust operation and authorization path before
   transport. No legacy global or platform back door performs the same effect.
4. **No authority globals.** An operation that reads identity or can confer an
   effect is module-bound and absent from the shared real global. A remaining
   shared global is grant-free and does not infer caller identity.
5. **Context is data.** Async work retains an immutable Rust context reference.
   The adapter never installs it as an ambient or thread-local current module
   while executing arbitrary JavaScript.
6. **Bearer delegation.** A bound callable or resource host object authorizes
   as its binding or resource record regardless of the caller's JavaScript
   stack. Raw JavaScript handoff transfers the same bearer; it does not create
   a new principal intersection or independently revocable child.
7. **Generation closure.** Runtime teardown and record revocation make all
   affected tokens unusable before their slots can be reused.
8. **Owner-thread JavaScript.** Rust workers and platform transports never
   enter JavaScript. Only the exact runtime owner thread may create, invoke, or
   release engine values.
9. **Shared-realm integrity.** The loader and intrinsic/global graph satisfy
   §6 before any project module or callback can execute.

## 3. Exact logical data model

These are normative logical records. Implementations may pack or intern them,
but validation must be observationally equivalent.

### 3.1 Runtime and record keys

```text
RuntimeKey {
  runtime_id: NonZeroU64,          // never reused in the process
  runtime_generation: NonZeroU64,  // changes before storage can be recycled
}

RecordKey {
  runtime: RuntimeKey,
  kind: Context | Binding | Callback | Completion | Buffer | Resource,
  slot: NonZeroU32,
  slot_generation: NonZeroU32,
}
```

`runtime_id` and `runtime_generation` are Rust-owned. A `RecordKey` is an
internal lookup key, not proof of possession. Generation numbers prevent stale
reuse; they are not the authority-forgery defense.

The adapter represents possession with a `NativeToken`: an engine-native,
non-enumerable, non-serializable value stored only in a host-function closure
or private host-object slot. There is no JavaScript constructor, decoder,
`valueOf`, clone format, or dispatcher accepting its scalar representation.
The adapter may carry a `RecordKey` inside `NativeToken`, but project code can
neither read nor synthesize that key. Copying the JavaScript callable or host
object copies possession of the same token.

### 3.2 Capability context

```text
CapabilityContextRecord {
  key: RecordKey(kind = Context),
  actor: PrincipalId,
  constrained_principals: NonEmptySet<PrincipalId>,
  static_grant_projection: GrantProjectionId,
  policy_generation: NonZeroU64,
  revocation_cell: RevocationCell,
  posture: PerModuleVanilla | AmbientCompatibility | Insecure,
  state: Live | Revoked | Closing | Closed,
}
```

The authenticated module loader, not JavaScript and not the engine, supplies
`actor` and the grant projection. `constrained_principals` contains `actor` and
represents constraints applied when Rust mints or attenuates the context; it is
not reconstructed from the call stack or Promise scheduler. A posture is part
of the context so a token minted for a compatibility or insecure runtime
cannot be interpreted as a per-module secure token.

The context record is immutable except for its revocation cell and lifecycle
state. Each runtime has one current policy generation. Policy mutation
increments that generation atomically before the new policy is observable;
every context and binding minted under the previous generation is stale and
must be replaced. Validation requires exact equality with the current
generation, never a policy-defined compatibility shortcut.

### 3.3 Operation binding

```text
BindingRecord {
  key: RecordKey(kind = Binding),
  context: ContextKey,
  operation: OperationId,
  lane: Inline | Async,
  attenuation: OperationAttenuation,
  parent_binding: Optional<BindingKey>,
  revocation_cell: RevocationCell,
  state: Live | Revoked | Closed,
}
```

`lane` MUST equal the generated operation descriptor. `attenuation` is typed
for that operation; an untyped string or JSON policy is not admitted at the
invocation seam. A binding authorizes only its recorded operation. The engine
adapter creates one host callable whose closure contains the binding's
`NativeToken`; the callable does not accept an operation ID or context token
from JavaScript.

Every operation descriptor additionally declares
`binding_requirement = GrantFree | ContextRequired`. `ContextRequired`
includes all identity-reading operations even when the operation needs no
user-configurable grant. Timers that retain an actor are `ContextRequired`;
pure encoding may be `GrantFree`. A shared callable is allowed only for a
`GrantFree` descriptor whose implementation never reads context or confers a
grant. The descriptor also declares argument conversion as `PrimitiveOnly` or
`Observable`; the latter enumerates the exact Web-specified property reads or
coercions that may execute project code and trigger reentrancy.

### 3.4 Callback, completion, buffer, and resource records

```text
CallbackRecord {
  key: RecordKey(kind = Callback),
  engine_callback: OwnerThreadEngineValue,
  state: Live | Released | Closed,
}

CompletionRecord {
  key: RecordKey(kind = Completion),
  binding: BindingKey,
  retained_context: ContextKey,
  callback_or_promise: CallbackKey,
  operation: OperationId,
  cancellation: CancellationState,
  state: Admitted | Completing | Settled | Cancelled | Closed,
}

ResourceRecord {
  key: RecordKey(kind = Resource),
  resource_kind: ResourceKind,
  owner_context: ContextKey,
  attenuation: ResourceAttenuation,
  parent_resource: Optional<ResourceKey>,
  revocation_cell: RevocationCell,
  payload: RustOwnedResource,
  state: Live | Revoked | Closing | Closed,
}
```

A `CallbackRecord` intentionally carries no ambient capability context. A
callback may lexically close over bound callables, but invoking the callback
does not install the completion's context for unrelated JavaScript calls.

A `CompletionRecord` retains context for Rust authorization, audit, resource
validation, and safe settlement only. Its callback is invoked on the owner
thread after revalidation. A `BufferRecord` follows the resource key/lifecycle
rules but contains bytes rather than external authority.

A worker or transport receives only a cloneable, opaque `CompletionLease` and
typed transport inputs. The lease contains no JSI/engine value and cannot
settle or release a callback directly. The owner-runtime slot exclusively owns
engine roots; owner-thread settlement or teardown consumes/releases them
exactly once, while duplicate producer results are refused.

JavaScript sees a resource as a host object with a private `NativeToken`.
Methods are operation-specific native callables bound to that resource; no
public API accepts `HostHandle::raw()`. Numeric timer IDs MAY remain for Web
compatibility because they are identifiers, not authority: `clearTimeout` and
ref/unref use the caller's bound timer operation and Rust checks that context
owns the timer.

## 4. Rust/engine adapter contract

The following operations define the logical seam; names are illustrative but
their inputs and effects are normative.

| Operation | Required behavior |
|---|---|
| `mint_context(authenticated_module, posture)` | Rust authenticates the module and returns a private `ContextKey`; the engine cannot supply a principal. |
| `bind_operation(context, operation, attenuation)` | Rust validates context, descriptor, grants, and attenuation, creates `BindingRecord`, and returns a token only to the adapter. |
| `derive_binding(parent, attenuation)` | Rust proves the attenuation is a subset, links revocation ancestry, and returns a distinct binding. |
| `invoke_inline(binding, typed_args)` | Performs the Rust portion of §5.1 synchronously and returns a typed value or `HostError`; it never waits on transport or invokes project code. |
| `admit_async(binding, typed_args, callback)` | Performs §5.2 admission, retains a completion record, and starts transport only after authorization. |
| `complete(completion, result)` | Revalidates runtime and completion, queues owner-thread settlement, and never runs JavaScript on the transport thread. |
| `mint_resource(context, kind, attenuation, payload)` | Creates an opaque resource record only after the owning operation authorizes the exact resource stage. |
| `derive_resource(parent, attenuation)` | Creates a subset authority and linked revocation ancestry. |
| `revoke(record)` | Atomically marks the record revoked and invalidates dependent admissions before returning. |
| `begin_teardown(runtime)` | Performs §9 and prevents new binding, admission, or callback creation. |

The engine adapter may translate JavaScript primitives, copy or borrow buffers
under their lifetime contract, retain/release engine values on the owner
thread, and enqueue owner-thread tasks. It MUST NOT mint principals, choose
grants, authorize resources, repair a missing token, infer a caller, or execute
transport after a Rust refusal.

## 5. Invocation protocol

### 5.1 Common validation and inline invocation

On every bound call, the implementation performs this order:

1. obtain the binding token from the native closure, never from arguments;
2. validate token kind, runtime/slot generations, binding and context state,
   posture, exact current policy generation, and every revocation ancestor;
3. resolve the fixed descriptor and verify its lane and conversion class;
4. for `PrimitiveOnly`, convert without executing project code; for
   `Observable`, perform only the descriptor's enumerated reads/coercions;
5. after any `Observable` conversion, repeat the complete step 2 validation;
6. atomically authorize and commit the operation admission/effect against the
   revalidated generations and revocation cells;
7. execute the Rust implementation; and
8. translate the typed result or safe refusal.

Steps 1–3 precede any user-observable argument access. Observable conversion
may reenter Ibex, mutate policy, revoke a record, or start teardown, which is
why step 5 is unconditional for that class. The Rust operation body itself
does not invoke project code. An inline operation is bounded owner-thread
computation: it MUST NOT wait on a worker, transport, contended service, or
project callback.

Unknown operations, wrong lanes, and malformed tokens fail before service
dispatch. Pure operations may use a context-free binding, but they still use a
fixed operation closure rather than a JavaScript-selected operation ID.

### 5.2 Async admission and completion

Async admission performs the same conversion-class and post-conversion full
revalidation. It then atomically authorizes, allocates the completion record,
and marks it `Admitted` before exposing work to a worker or transport. For
staged VFS or network operations, `Staged` is not an allow: the paired service
MUST prove it performs the specified Requested/Discovery/Commit/Repeat checks,
and transport cannot pass a stage before Rust authorizes the exact discovered
resource.

Completion follows this order:

1. the transport produces typed data or a transport failure without entering
   JavaScript;
2. Rust uses the producer's `CompletionLease` to offer the result exactly
   once, without touching engine state;
3. Rust validates the runtime, binding/context, resources, policy generation,
   revocation, cancellation, and final authorization stage;
4. the result enters the unified owner-task queue under §8's transactional
   admission rule; temporary queue failure retains it for retry, while Closing
   gives it the terminal drop/dispose outcome;
5. the owner task repeats step 3 plus callback validation; successful delivery
   then marks `Settled`, while revocation/teardown drops without that state; and
6. Hermes performs the Promise/microtask checkpoint required by §8.

Late, duplicate, cross-runtime, cancelled, or stale completions never invoke
project code. A denial or teardown cannot be converted into successful
transport by an adapter race.

## 6. Module binding, globals, and bootstrap

### 6.1 Bootstrap order

The vanilla secure bootstrap is a no-project-code, no-job critical section:

1. create the runtime and capture pristine public intrinsics;
2. install only construction-private native adapters needed to build the
   module factory and stdlib bindings;
3. capture those adapters into unreachable native/loader state;
4. delete every construction-private property, including spellings such as
   `__ibex2ReadFile`, and verify deletion/non-reachability;
5. freeze the shared intrinsic and global graph required by LLP 0058.000 D8;
6. create and cache module bindings through Rust-authenticated contexts; and
7. only after all prior steps succeed, enable project evaluation and engine
   job execution.

No Promise job, timer, finalizer, module body, getter, proxy trap, extension,
or embedder callback may run between steps 2 and 5. Any failure destroys the
runtime; it does not continue in a partially armed posture.

The freeze uses a generated, versioned root inventory rather than an
open-ended walk from attacker-controlled values. Using captured pristine
descriptor/prototype operations, it traverses own data-property values and
prototypes without reading accessors, freezes post-order, then verifies the
expected descriptors, prototypes, non-extensibility, and explicitly declared
mutable exceptions. An unexpected accessor, proxy/exotic behavior, thrown
reflection result, unfreezable node, missing root, or extra authority-bearing
root refuses bootstrap. The inventory and exception list are receipt-bound;
tests against the selected stock pin prove the algorithm executes no project
code or engine job.

### 6.2 Module surface

The loader injects an immutable module-scoped stdlib namespace or fixed
factory parameters. A bound namespace cache key is exactly:

```text
(RuntimeKey, ContextKey, BindingProfileId, StdlibSurfaceVersion)
```

It is never keyed only by principal name: two contexts for one principal may
have different grants, constraints, policy generations, or revocation cells.
The namespace and its binding properties are non-writable and
non-configurable. Capability-bearing bindings are absent from `globalThis` and
from any prototype reachable through the namespace.

The one logical secure ABI is:

```text
FactoryV1(module_record, import_function, stdlib_namespace) -> exports
```

The artifact receipt binds `FactoryV1`, shape/format version, code digest,
`BindingProfileId`, and `StdlibSurfaceVersion`. Source, CommonJS, lowered ESM,
prepared source, and HBC are supported only when the authenticated build emits
that exact factory shape; factory construction and invocation occur through
public engine interfaces. Direct eval, pre-existing HBC that performs global
authority lookup, and native ESM lacking authenticated binding injection are
unsupported and refuse before project code. The loader MUST NOT rewrite free
globals, retrofit arbitrary bytecode, emulate compartment-global lookup, or
fall back to a root/application context.

### 6.3 Shared values

ECMAScript intrinsics and grant-free helpers may be shared only after the D8
integrity freeze. `queueMicrotask` may be shared if it confers no grant and
never reads identity. Actor-retaining timers, filesystem, network, storage,
crypto keys, native extensions, diagnostics with effects, and similar APIs are
module-bound. A diagnostic API on the real global must be provably grant-free
or absent. A non-empty authenticated runtime-extension registry remains on the
patched tier until an accepted LLP 0040 amendment defines an equivalent Rust
binding/completion carrier and removes the patch-export gate; vanilla does not
silently omit that constraint while enabling extensions.

## 7. Delegation, attenuation, and revocation

Passing, exporting, re-exporting, storing, or scheduling a bound callable or
resource host object transfers that same bearer. Importing a re-export does
not intersect its grants with the importer's context. A call from
`Promise.then`, a timer callback, or an empty JavaScript stack authorizes as
the binding. This is explicit delegation under LLP 0058.000 D5, including
`Promise.resolve(x).then(deputy.readFor)`.

Raw JavaScript transfer creates no new Rust record. It is therefore not
independently attenuated, revocable, or attributable to a recipient; revoking
the shared original affects every holder. Code needing a subset, separate
revocation, or auditable delegation MUST ask Rust to derive a binding or
resource.

For derivation:

- the child operation/resource kind MUST equal the parent kind unless an
  operation contract defines a one-way projection;
- child grants, resource scope, methods, stage rights, expiry, and quotas MUST
  be subsets of the parent;
- a child has its own revocation cell and an immutable parent link;
- revoking a child does not revoke its parent or siblings; and
- revoking/closing any ancestor makes every descendant fail validation before
  effect or transport.

Attenuation failure is `CapabilityDenied` or `InvalidArgument` and never
silently returns the unattenuated parent.

Validation walks a receipt-bounded ancestry of at most
`MAX_DELEGATION_DEPTH`; attempting a deeper derivation refuses with
`ResourceExhausted`. Race outcomes are fixed by these linearization points:

| Race | Required outcome |
|---|---|
| policy replacement vs. call | generation increments before publication; a call not yet committed under §5 refuses stale policy |
| revoke/close vs. admission or resource stage | the revocation/state transition wins until the authorization-and-admission/stage commit; afterward the committed effect is not recalled |
| revoke after an async effect commit | later stages and owner-thread delivery revalidate and may refuse/drop even though the external effect cannot be undone |
| timer clear/revoke vs. delivery | delivery revalidates its binding/context immediately before callback invocation; an uncommitted delivery drops |
| completion vs. queue pressure/teardown | temporary admission failure retains the result for retry; Closing produces one terminal dispose outcome |

The implementation may use locks, epochs, or atomics, but it MUST expose these
outcomes and never validate an ancestry from a mixture of generations.

## 8. Tasks, microtasks, timers, and callbacks

Rust owns one sequence-numbered FIFO of admitted host tasks, including timer
deliveries, async settlements, and subscribed host events; Hermes owns
Promise/microtask semantics. Admission assigns the sequence while holding the
same queue lock which appends the task, so two publishing threads cannot
receive sequence numbers in an order different from the FIFO. The owner-thread
outer driver has this state machine:

```text
Idle -> PreCheckpoint -> ReservedHostTask -> RunningHostTask
     -> PostCheckpoint -> Idle
any non-Closed state -> Closing -> Closed
```

A depth-zero drive cycle performs the following exact order:

1. `PreCheckpoint` drains all engine microtasks already queued, using the
   selected stock pin's public checkpoint API.
2. Rust reserves at most the oldest ready FIFO task. Reservation is not an
   irreversible timer/completion transition.
3. On the owner thread, the adapter revalidates the task's runtime, callback,
   binding/context, policy, revocation, and resources. It then commits exactly
   one source transition and invokes/settles it without installing an ambient
   principal/context.
4. If invocation/settlement cannot be committed, Rust either rolls the task
   back to its same FIFO position for retry or records one terminal
   cancellation/teardown disposition; it never loses a live task after
   removing it from its source.
5. After the host task returns, `PostCheckpoint` drains the engine microtasks
   it caused before the next Rust task may be reserved.

Only one Rust host task runs per cycle. A drive request made while the driver
is not `Idle` records a wakeup; it never nests a Rust pump or starts a second
host task inside project JavaScript. Subject to each callback and microtask
checkpoint terminating, every ready FIFO task progresses; an infinite
JavaScript callback or microtask chain is availability failure outside the
vanilla threat claim. A microtask invoking a bound callable uses that token. A
plain callback gains no ambient authority from a completion record.

**The deadline (2026-09-10).** "Availability failure outside the claim" was
the whole story until a consumer ran code it does not trust with time:
Snapback 2's effects, whose ticket of 2026-09-01 found that nothing could
stop `while (true) {}` — not its thirty-second budget, not `dev --stop`,
because none of the adapter's entrances could be interrupted. The adapter
now carries **one deadline per runtime**, a point on the monotonic clock
armed by `Hermes::set_deadline(Instant)` and disarmed by `clear_deadline`,
and every entrance into JavaScript — `eval`, `eval_bytes`,
`drain_microtasks`, `pump`, `run_entry` — is held to it:

- At the door, an entrance whose deadline has passed is **refused** without
  running anything. Otherwise the pin's public time-limit monitor
  (`HermesRuntime::watchTimeLimit`) is armed for at least the time that is
  left, rounded up to the next millisecond — what remains of the same
  deadline, never a fresh budget per entrance or per drain iteration — and
  released on every way out. The monitor counts in milliseconds; the clock
  decides the outcome, so the rounding can only delay a stop, never bring
  one early. The refusal boundary is as fine as the steady clock's tick: on
  a clock coarse enough, an entrance on the same tick as a deadline that is
  due is admitted and reported at exit, not refused.
- While JavaScript runs, the monitor's request is honoured at the
  interpreter's `AsyncBreakCheck` sites, which `AsyncBreakCheckInEval` —
  **pinned on at construction** beside the microtask queue, never trusted
  to the pin's default, because the deadline's stop depends on it — emits
  at every loop back-edge and every return of evaluated source — so a
  callback is stopped after it has scheduled its successor, and a
  self-scheduling microtask chain is paused rather than killed; only a
  deadline keeps a later drain from resuming it. The engine raises its
  timeout as an **uncatchable** error
  (`Runtime::raiseTimeoutError` in the pinned source), so JavaScript cannot
  swallow it. Bytecode carries only the checks it was compiled with; hermesc
  emits none by default, so such a program runs to its end and is reported
  at exit. An adapter therefore must not arm a deadline as its only bound
  for precompiled bytecode it does not trust with time: what stops such a
  program is the checks it was compiled with, or a bound of the consumer's
  own outside the runtime.
- The outcome of an entrance that ends past its deadline is the deadline —
  `JsError::Deadline`, a distinct checked result from every entrance —
  classified by the clock and never by the text of what was thrown, which is
  JavaScript's to forge. Nothing JavaScript did on the way is reported. A
  pump the deadline stops abandons its task with no post-checkpoint and
  releases the drive flag like every other exit, so the next cycle is not
  refused as nested.
- The monitor fires once and leaves its request pending when nothing was at
  a check. An entrance that ends past its deadline flushes that request with
  one empty program before returning, so a runtime whose deadline fired is
  reusable once the deadline is cleared; its JavaScript state is whatever
  the stop left, which is the consumer's to judge.
- `set_deadline` and `clear_deadline` are owner-thread calls like every
  entrance (§2, invariant 8): the deadline is read at each entrance without
  synchronization, so arming or clearing it from another thread races an
  entrance in flight.
- The helpers that block *between* entrances — `pump_until` and
  `run_to_quiescence` — cap every wait by the time left and return once the
  deadline has passed; no wait outlives it. Their return values do not say
  whether the deadline or quiescence ended them; a caller that must tell
  the two apart checks its own clock against the deadline it armed.
- Teardown runs no JavaScript and needs no deadline.

A microtask checkpoint a job throws out of — only an engine-raised error
can; Promise reactions and `queueMicrotask` catch their own — is reported
as an uncaught error and resumed behind the job, which the engine retired
before running it. Before the deadline landed, such a throw unwound through
the C ABI. `run_entry` drains the microtasks its module's body queued
through this same checkpoint, so the entry's drain is held to the deadline
and reports-and-resumes like a pump's; a failure to load or run the module
body itself remains the entry's own failure. A host task that fails natively
— the engine throwing out of a call or a settlement — is reported the same
way as one that throws in JavaScript; nothing unwinds through the C ABI
from any entrance.

The pin-level feasibility probe must exercise public factory invocation,
pre/post microtask checkpoints, callback invocation, exception reporting, and
runtime destruction with queued jobs. Failure of any operation keeps that pin
or module shape outside the vanilla profile; a Hermes-private job hook is not
an implementation option.

A timer record retains its creating timer binding/context, callback token,
arguments, deadline, sequence, interval, reference state, and lifecycle.
Timers with the same deadline fire by monotonically assigned sequence. The
adapter reserves exact timer identities so cancellation by an earlier callback
cannot consume the next timer. On delivery commit, intervals reschedule before
their callback so clearing within the callback removes the next occurrence;
one-shots retire before callback failure. Before that commit, failed queue
admission leaves the timer eligible. Ref/unref and clear are authorized by the
bound timer context, not by a current frame.

An event record retains its subscription identity and primitive payload. A
subscription's only operation is `unsubscribe`; dropping the Rust handle does
the same thing. Unsubscribe removes events which were admitted but have not
been reserved and prevents later admission. A delivery already reserved by a
pump may finish. This is the same commit boundary timers use: cancellation
does not unwind JavaScript already entered. Runtime teardown clears all live
subscription identities, while adapter detach releases the matching callback
roots. Publication checks subscription liveness and inserts the event into the
FIFO while holding the subscription registry lock, then releases that lock
before notifying the embedder or invoking its wake callback. Thus unsubscribe's
remove-then-cancel order closes the admission race without making a re-entrant
wake deadlock or poison the subscription registry.

## 9. Teardown and lifecycle

Runtime state transitions monotonically:

```text
Running -> Closing -> Closed
```

Entering `Closing` atomically prevents new contexts, bindings, resources,
callbacks, admissions, task commits, and transport stages. If requested while
project JavaScript is running, that frame may return to the adapter, but no
post-checkpoint or new project callback/job starts; queued Hermes jobs die with
the runtime. Reserved/uncommitted Rust tasks receive one terminal disposition.
Rust revokes records and marks cancellations, and workers may finish native
cleanup, but late results cannot settle JavaScript.

The owner thread releases every callback/object root exactly once before
engine destruction. Only then may record storage be recycled, with an
incremented slot generation; runtime IDs are never reused and generations
never wrap. Teardown is idempotent. A finalizer is cleanup advice, not the sole
revocation mechanism.

Native storage lifetime and runtime ownership are separate. A `Context` and an
owning engine runtime each hold an owner lease; worker/completion references do
not. The last owner lease atomically enters shutdown even if a worker still
retains the state to finish native cleanup. Before that owner release returns,
the wake callback is cleared and any invocation already claimed by a publisher
has finished. Queue closure and FIFO insertion are decided under the same lock:
a worker result offered after closure never enters the FIFO and its owned result
resources are dropped on the publishing thread. Blocked transports are
cancelled, SQLite begins shutdown, and no late worker invokes the retired
callback.

## 10. Refusals and safe materialization

The stable refusal classes are:

| Condition | Error code |
|---|---|
| malformed typed argument or invalid attenuation | `InvalidArgument` (or the operation's narrower validation code) |
| unknown operation | `UnsupportedOperation` |
| descriptor/call lane mismatch | `WrongInvocationLane` |
| grant, stage, posture, or delegation denied | `CapabilityDenied` |
| forged, wrong-kind, wrong-runtime, stale, revoked, or closed token | `StaleHandle` |
| cancelled admission or runtime closing | `Aborted` |
| table/generation/quota exhaustion | `ResourceExhausted` |
| platform or I/O failure after authorization | `Transport` (or the operation's typed failure) |
| violated internal invariant | `Internal` |

Token errors intentionally do not distinguish nonexistent from unauthorized
records. Refusal happens before effect and, for invalid provenance, before
user-observable argument access.

`HostError` is Rust-owned data containing a code, fixed operation ID, and safe
message with virtual/sanitized resource names only. The adapter materializes
the JavaScript error using captured pristine/native constructors. It MUST NOT
read properties from the thrown input, call `toString`, invoke getters or
proxy traps, consult a replaced prototype, or otherwise execute project code
while constructing a refusal. If safe error construction is unavailable, the
adapter emits a fixed minimal native error or terminates the affected runtime;
it never turns refusal into success.

## 11. Conformance requirements

A vanilla secure engine/profile pair conforms only if all tests below run
against the exact receipt-bound artifact.

### 11.1 Provenance and handle safety

- build/link scans prove no `currentPrincipalId`, principal-stack,
  thread-local identity, principal-zero, or ambient-root fallback path;
- no JavaScript-visible generic dispatcher accepts operation/context/resource
  scalar IDs;
- fabricated scalars, copied serialized objects, wrong-kind tokens,
  cross-runtime tokens, stale generations, revoked ancestors, and use after
  teardown fail before effect;
- resource host objects and binding functions work when possessed and fail
  after revocation; and
- numeric timer-ID guessing cannot clear/ref/unref another context's timer.

### 11.2 Global and bootstrap integrity

- capability-bearing and identity-reading surfaces are absent from the real
  global, prototypes, diagnostics, and construction-private bridges;
- `__ibex2ReadFile`-class bridges are captured and deleted before any job can
  run, including failure/reentrancy fixtures;
- poisoning `Promise.prototype.then`, constructors, prototypes, namespace
  objects, and global properties before/after the integrity boundary either is
  impossible, is detected and refuses bootstrap, or cannot discover a bound
  callable; and
- unsupported module and prepared-bytecode shapes fail closed.

### 11.3 Delegation and async behavior

- direct pass, import/re-export, `Promise.then(bound)`, timer scheduling, and
  detached invocation all authorize as the possessed binding;
- the same shapes without possession cannot discover authority;
- raw transfer shares revocation, while a Rust-derived child proves subset
  attenuation, independent child revocation, and ancestor revocation;
- a callback never gains the completion's context as ambient authority;
- same-deadline timer ordering, cancellation visibility, interval reschedule,
  one-shot retirement, and callback-failure behavior match §8; and
- every host task is followed by its Hermes microtask checkpoint before the
  next Rust task.

### 11.4 Authorization and effect closure

The generated inventory schema records each artifact entry root and effect
sink with one disposition: `Absent`, `Refuses`, or `Joins(OperationId)`. Its
authoritative inputs are the artifact entry-root manifest, generated operation
catalog, native/platform transport registries, extension and diagnostic
registries, bootstrap/global manifest, and legacy-spelling/link map. A build
fails for an unregistered reachable root or sink, a duplicate join, or a sink
without a disposition. Tests prove descriptor lanes/types/stages, no transport
after refusal, and exact VFS/network Requested/Discovery/Commit/Repeat joins.

### 11.5 Portability and refusal safety

- the contract suite runs through a minimal second/mock engine adapter using no
  Hermes-private symbol;
- all JavaScript engine access occurs on the recorded owner thread;
- refusal construction under hostile getters, proxies, `toString`, and
  replaced error constructors executes no project code; and
- duplicate/late completion and every teardown interleave settle at most once
  and never invoke JavaScript after closure.

## 12. Greenfield construction obligations

LLP 0058.000.001 supersedes incremental replacement inside the legacy adapter.
This protocol is implemented in a separate source/dependency closure with a
new composition root. At minimum:

1. the deny-all kernel record tables, operation catalog, task FIFO, and
   teardown exist before any project-code binding;
2. authenticated module loading mints contexts and invokes only receipt-bound
   `FactoryV1` artifacts;
3. every `ContextRequired` operation is a fixed native closure over a private
   token; no scalar context/resource entry point exists;
4. the new adapter contains no `currentPrincipalId`, principal-stack,
   thread-local, principal-zero/root fallback, legacy global installer, or
   generic JavaScript dispatcher path;
5. the §6 bootstrap and §8 driver are used by the first executable fixture,
   not retrofitted after broader API work;
6. unimplemented operations are absent, and a greenfield runtime cannot call
   the legacy runtime as an API, module, effect, or artifact fallback;
7. audited algorithm and platform reuse enters only through the dependency and
   typed-service rules of LLP 0058.000.001; and
8. the closed-world inventory and this Spec's suite pass against the exact
   linked upstream artifact before secure selection.

The patched tier remains authoritative until accepted LLP 0013 deputy/audit,
LLP 0039 selector, LLP 0040 extension-carrier, and LLP 0059.000 lane/timer
amendments admit this contract, or a conforming replacement tier exists.
